# py_yupei_pair 配对循环提速：九遍扫描并三遍 + 六个矩数组向量化

改动位置：`src/yupei_pair/net.rs`（配对循环内）、`src/yupei_pair/simd.rs`（新增
`fused_hg_stats` / `argmax_first_two` / `mass_acc_hg`）。
基线：v4（家族裁剪 + net/topk 合并扫描）之上。补丁见文末。

## 一、改了什么

一个配对 (B,C) 里，n=5107。原来对 h、g 两个数组做 9 遍独立扫描。

| 原来的遍 | 干什么 |
|---|---|
| 1 | `fill_h` 算 h = wb·p + wc·q + addm |
| 2 | `fill_gap` 算 g = h − max(p,q) |
| 3、4 | `argmax_first(hb)`：先扫最大值，再扫第一个等于最大值的下标 |
| 5、6 | `argmax_first(gb)`：同上 |
| 7 | `pos_stats`：Σrelu(h)、Σrelu(g)、Σrelu(g)²、#(g>0) |
| 8 | `mass_acc_h`：六个矩数组里的三个 |
| 9 | `mass_acc_g`：另外三个 |

现在并成 3 遍：

1. `fused_hg_stats`：算 h、g 并写回（b、c 位置直接写 −inf），同一趟累计两个最大值的
   8 路 max 累加器、`pos_stats` 的三个 8 路和累加器与计数（遍 1、2、3、5、7 合成一遍）。
2. `argmax_first_two`：一趟同时找 h、g 里第一个等于最大值的下标（遍 4、6）。
3. `mass_acc_hg`：一趟里对每个 x 先做 h 口径、再做 gap 口径的六个矩数组更新（遍 8、9），
   并且这六个数组的逐元素更新改成 AVX2 一次 8 个。

## 二、为什么数值逐位不变

1. h 的算式一字未动（向量路径 `add(add(mul(wb,p), mul(wc,q)), addm)`，标量路径
   `wb*p + wc*q + addm`，不用 fma）；g 仍是 `h − max(p,q)`，向量用 `_mm256_max_ps`、
   标量用 `if p>q {p} else {q}`，与原 `fill_gap` 一样。
2. 最大值与 `pos_stats` 的归约顺序不变：8 路累加 → 按 lane 0..8 依次归约 → 尾巴按 x
   升序处理；尾巴仍是「先 lane 归约、再加尾巴」。
3. b、c 两位置原来在 fill 之后单独置 −inf，现在在第一遍里直接写 −inf，后续 argmax 与
   topk 看到的数组内容一致；含 b/c 的那个 8 宽块改成标量算 8 个元素，但按原 lane 位置累加。
4. 下标查找仍是 x 升序、先到先得；`mx_g` 为 −inf 时按原语义不扫 g。
5. 六个矩数组是逐元素独立累加，没有跨元素归约，所以 8 个一组与逐个算逐位相同；
   `h>0` / `g>0` 用比较掩码实现，掩码为假的通道把「要加的数」用 and 清零后仍然相加
   （加 +0.0 对这几个初值 0.0、只增正数的数组是恒等；乘法在掩码为假时可能得到的 NaN
   也在 and 这一步被清成 +0.0）。「和大于 0 才累加」两个条件照旧。

## 三、实测（20241231、单张 cnt_t1、10 并行、队列 200 进程同时在跑）

### 测速口径（定死的规则）

1. **判断改动有没有用，只看同一段代码在同样队列状态下的那一行**，即
   `[net:cnt_t1] 扫描`。这一行是同一段代码、同一台机器、同样并行数、队列都是 201 个
   进程、负载 216~260 的时候量的：v4 91.5 秒、v5 73.1 秒、v6 57.3 秒。
2. **跨时刻的总时间只当旁证。** 同一份 v5 代码单张总时间测到过 480.88 秒和 282.56 秒
   两次（相隔 15 分钟，队列都在跑），差 70%，那是队列抢盘造成的。v5 的 1485.46 秒与
   v6 的 1168.67 秒虽然都是队列在跑，但不是同一时刻，只能当旁证。
3. **空机器的数不能当改前基线。** v4 的 1745.49 秒（10 并行、空机器）只当参考，
   v6 的 1168.67 秒是队列 201 进程时量的，两者不可直接比。
4. 以后每报一个秒数都要写明当时的机器状态：队列有没有在跑、跑了多少进程、多少并行。

| 版本 | net 扫描段 | 相对 v4 |
|---|---|---|
| v4（家族裁剪 + net/topk 合并） | 91.5s | — |
| v5（九遍并三遍） | 73.1s | −20% |
| v6（再加六个矩数组向量化） | 56.6s | −38% |

50 并行下的标准口径（20241231、默认 15 张、机器空载）还没跑，参考数是改前 423.41 秒、
v4 392.23 秒。net 扫描段在 50 并行、v4 下是 278 秒（占整趟 71%），按同一比例推算 v6 约
172 秒，整趟约 286 秒，但这是推算，必须实测。

## 四、试过但没用的三条路（如实记录）

1. **把选择用的键从 8 字节压到 4 字节**（只用降序键选前 500，同分再按下标补齐）：
   数值错（`select_nth_unstable` 会就地打乱数组，打乱后位置不再等于原下标），而且更慢。
   这条路已放弃。
2. **256 桶先粗后细选择**（按降序键高 8 位统计，找第 take_t 名落在哪个桶，再收候选）：
   数值对（单张 0 个不同），但慢一倍（107.0 秒 vs 56.6 秒）。原因是直方图那一步是
   对同一小块内存的连续读改写，相邻元素的桶号常常相同，形成串行依赖链。
3. **打包键 8 个一组（AVX2）**：数值对，速度没变（56.8 vs 56.6），说明那一段的瓶颈
   不在打包本身。这条没有留下。

## 五、验证方法与结果

1. 单张 `mats=["cnt_t1"]`（5107 × 701 = 3,580,007 个值）与改前存档逐位比：
   **不同 0 个，NaN 位置不一致 0 个**。v5、v6 各跑过一遍，都是 0。
2. 默认 15 张（5107 × 10515 = 53,699,505 个值）与改前存档逐位比：**不同 0 个，
   NaN 位置不一致 0 个**，股票顺序与列名顺序一致。v5、v6 各跑过一遍，都是 0。
   v6 那次的机器状态：2026-10-13 14:44 起、默认 15 张、10 并行、队列 201 个进程同时
   在跑、负载 216~260，跑了 23 分钟；该次默认 15 张总时间 1168.67 秒。
3. 换线程数结果一致：10 并行与 50 并行各跑一遍，两份结果逐位比（50 并行那趟待跑）。
4. 标准测速：20241231、默认 15 张、50 并行、机器空载（待跑）。
