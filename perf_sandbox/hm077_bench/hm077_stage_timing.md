## 二、怎么拆的

hm077.rs 里的读盘、排序、`ultra_sorted_v2` 三块是自洽的（只依赖标准库），
所以直接把源码第 104~986 行原样抽出来编成独立程序，不重写逻辑，只把数据路径写死。
先核对行数：抽取出来的 `read_day` 跑出 **132,032 行**，与按同样的读盘口径在 Python 里复刻的结果一致。

剩下的部分（dropna、24 列统计那 16 块）依赖库里的 features_f64，没法单独抽出来，
所以用「总时长减去已测部分」得到。

## 四、为什么这一步贵

`ultra_sorted_v2` 的做法：先把逐笔按订单号聚合成订单（这一步 13.5 万个订单），
再按「订单总量」分组，一共 1,047 组；然后在每一组里，对每一条订单，把同侧（same）
或对侧（diff）的**所有**订单都拉出来，建一个「时间差 + 价格」的表，按时间差排序。
所以每个订单要看一遍同组里同侧的全部订单，元素总数正比于组内订单数的平方。

实测的规模：

- 订单数 134,789，按订单总量分成 1,047 组，其中规模 ≥100 的有 80 组；
- 最大的 10 组规模：20,956 / 15,050 / 11,496 / 11,011 / 7,818 / 6,256 / 5,413 / 3,759 / 3,217 / 3,188；
- same 方向元素数 = 6.1445e8，diff 方向 = 5.1901e8，合计 1.13e9；
- 实测 37.32 秒 ÷ 1.13e9 = 33 ns 每元素。

33 ns 这个单价高于 hm076 同款循环（15.8 ns）的原因不是写法，是这一版每个元素要建一个二元组、
再排一次序：先 filter+collect 复制一遍同侧订单，再建 (时间差, 价格) 元组排一次，价格还要单独排序一次。

不是内存分配导致的：分配次数虽多（每条订单两个 Vec），但按元素算的单价与复用 buffer 的 hm076 那一段是同一量级，
真正决定时间的是元素总数 1.13e9。

不是读数据：132,032 行的 CSV 读+解析 190.6 ms，占 0.5%。

## 五、和 hm076 的对比（同一个 notebook 出来的姊妹系列，瓶颈不一样）

| | hm076（77 个因子，28.81 s） | hm077（55 个因子，39.52 s） |

| 读 + 变换 + 排序 | 50.8 ms / 0.2% | 227.9 ms / 0.6% |
| 组内两两循环 A（ultra_sorted 主循环） | 7,575 ms / 26.3% | 37,322 ms / 94.5% |

hm077 少了 v3 那一段，反而更慢：它走的是 v2 入口，按 ask/bid 两列各记一笔订单，
13.5 万个订单里 is_bid 占 43.9%、ask 侧 56.1%，两侧都很大，
组内两两的距离元素 1.13e9 个；hm076 那一段只有 4.79e8 个。

## 六、每个因子

39.52 s ÷ 55 = **719 ms/因子**。用户的标准是单股单日 1 秒，
按整个单元算是 39.5 倍，按单因子算是 0.72 倍。两个口径差别很大，这里都写明，口径由用户定。
