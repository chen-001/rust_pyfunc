## 二、实测并行利用率

采样命令：`cat /proc/loadavg`、`/proc/stat` 8 秒差值、`ps -eo pid,ppid,pcpu,comm`、逐个 `/proc/<pid>/stat` 累加 utime+stime。

| 指标 | 实测值 |
|---|---|
| load average（调查期间区间） | 1 分钟 231.9–349.2，5 分钟 218.8–295.2，15 分钟 214.4–251.7 |
| `/proc/stat` 8 秒采样整机 | busy 46.5%–50.1%，idle 49.7%–53.3%，**iowait 0.2%–3.2%** |
| 工作进程数 | **恰好 200 个** `rust_pyfunc_worker`，PPID 全是 2338178 |
| 工作进程状态 | `ps` 显示 **200 个全是 R（在 CPU 上）**，0 个 S、0 个 D |
| 单进程 CPU | 94.2%–97.1%（`ps -o pcpu`） |
| 200 个 worker 合起来 | 8 秒实测 **198.4 核**（utime+stime 差值 ÷ 8 秒） |
| 占分给它的 200 核 | **99.2%** |
| 占整机 512 核 | **38.8%** |
| 父进程 hm32 自己 | 1.2% CPU（纯调度），468 个线程 |
| 其余 CPU | 整机 busy 236–256 核，减去我们的 198.4 核，其他会话占约 38–56 核 |

结论：**200 个 worker 全部在算，没有一个在等 I/O 或空转**；机器还有一半核闲着。

## 三、为什么是 200 而不是更高

没有任何代码把它夹到 200。唯一的硬约束是 `RUST_PYFUNC_CPU_BUDGET`（`factor_production.py:30`），
而这个值就是 `hm32.py:237` 按 `FACTOR_N_JOBS` 自己写进去的 200。逐项排查限制因素：

| 可能的限制 | 实测 | 是否成为限制 |
|---|---|---|
| 内存 | 整机 1511 GB，用掉 65 GB；200 个 worker **合计 RSS 9.61 GB，平均 48 MB** | 否，可用 1433 GB |
| 文件描述符 | 父进程 **428 个句柄** = 400 根 worker 管道 + 24 个 colblk（8 分片 × 3）+ 2 日志 + 1 锁 + /dev/null | **是，最接近的一项** |
| 文件描述符上限 | `/proc/2338178/limits` 软上限 **1024**，硬上限 1048576 | 按 `2N+28 ≤ 1024` 反推，**天花板约 498 个 worker** |
| 数据盘读带宽 | iowait 0.2%–3.2%；/ssd_data 与 /nas197/user_home 都在 nvme2n1，8 秒实测读 **140.3 MB/s** | 否，NVMe 远未打满 |
| 磁盘 I/O 等待 | 200 个 worker 里 D 状态 0 个 | 否 |
| 任务分片粒度 | `待处理任务: 11399112`，每任务约 2.07 CPU 秒 | 否，粒度足够细 |
| CPU 核数 | 512 核，我们的 200 个 worker 被绑在 0-199，其他核空着 | 否 |

所以「为什么是 200」的答案是**没有技术理由**：一个未提交的手工常量，
而它同时决定了绑核范围（0-199），把任务锁死在 200 个核里。
真正会挡住 400 以上的是软句柄上限 1024（498 个 worker 左右开始 EMFILE），不是内存、不是盘。

另有一层：`queue_runner.py:76` 把守护进程的 `max_concurrent` 设成 1（`/api/config` 实测 `{"max_concurrent":1,"running":1,"pending":0}`），
一次只跑一个系列，整台机器就靠这一条线的 200 核撑着。

## 四、400 并行能省多少小时 —— 本节作废，禁止引用（200 是用户标准值）

先给依据：worker 已经 99.2% 忙，墙钟时间等于「总 CPU 工作量 ÷ 分到的核数」，
不存在等待型开销，所以核数翻倍，墙钟时间减半。这一条由上面的 198.4/200 核和 0 个 D 状态进程支持。

**本次 hm32（PID 2338178）**

| 项 | 数字 | 来源 |
|---|---|---|
| 任务总数 | 11,399,112 | 日志 `📋 待处理任务`，与 `hm32.py:319` 的 20150105–20260918 对得上 |
| 已完成 | 9,488,715（**83.2%**） | `hm32.log` 2026-10-12 00:29 |
| 剩余 | 1,910,397 | 相减 |
| 稳定速度（近 20 小时） | **96–98 任务/秒** | 日志 `速度:` 字段 |
| 已用 / 自报剩余 | 27.4 h / **5.5 h** | 同上 |
| 单任务成本 | 198.4 ÷ 96 ≈ **2.07 CPU 秒** | 实测核数 ÷ 速度 |
| 按 400 并行重算 | 1,910,397 ÷ 196 ≈ 2.71 h | 速度为 2 倍 |
| **本次可省** | **约 2.7–2.8 小时** | |

**整个系列的 base 阶段**

- 11,399,112 ÷ 98 ≈ **32.3 小时**（200 并行）
- 400 并行约 **16.2 小时**，**省约 16 小时**
- 收尾阶段（`run_db`/`run_h5`/`run_h1` + 24 个 fold）不吃并行数，但很小：
  历史上 hm24/hm26/hm27/hm31 的 worker 阶段占总墙钟的 **90.6% / 98.3% / 98.2% / 97.1%**，
  收尾只有 6–9 分钟

**队列整体**

- `program_state.json`：89 个系列，`step_submit` 为 pending 的 **64 个**，done 24 个，running 1 个
- 已完成、200 并行的 5 个系列（hm26/hm28/hm2/hm30/hm31）平均 2.75 h/个
- 按每系列 base 阶段减半估算，64 个系列合计可省约 **90–130 小时**（3.8–5.4 天）

**开到 400 的代价（实测外推，都能算出来）**

| 项 | 200 并行现状 | 400 并行预计 | 余量 |
|---|---|---|---|
| 父进程句柄 | 428 | 828 | 软上限 1024，够但已是最近的一项 |
| worker 内存 | 9.61 GB | 19.2 GB | 可用 1433 GB |
| 占用核数 | 198.4（绑 0-199） | 约 396（绑 0-399） | 整机 512，其他会话约 38–56 核 |
| 超过约 498 个 worker | — | 父进程会 EMFILE | 想再往上必须先抬 `ulimit -n` |

## 五、口径说明

- 「400 并行省一半」是从 worker 满载（198.4/200 核）和共享资源余量推出来的，不是同系列 A/B 实测；
  任务库里没有同一系列在 200 和 400 下各跑一遍的记录。
- 日志里不同系列的速度（hm24 941.7/s、hm26 529.2/s、hm27 547.1/s、hm31 693.5/s、hm32 96/s）
  差别来自每个任务本身的轻重，不是并行数，不能横向当作并行效率比。
- hm32 起步约 3 小时速度只有 56–75 任务/秒，之后稳定在 96–98；上面的估算用的是稳态值。
