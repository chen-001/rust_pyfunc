# _fold 因子计算路径实测（sandbox，不改正式库）

陈冲冲的结论是：hm032 每因子 26.6ms、hm031 每因子 4.7ms，差 5.8 倍，根因是 hm32 的 24 个 _fold
因子走 Python。实测下来前半段（数字）对得上，后半段（归因）不成立。

## 一、_fold 因子不在"每个计算单元"这条路上

- `src/okay_database/hm032.rs` 每个单元只产出 110 个 unfold 值，_fold 不在里面。
- 24 个 _fold 由 `reports/okay_database/submit/hm32.py:241 _write_fold_factors` 在
  **base 全部写完之后**跑一遍：逐个 unfold 因子把整块 base 面板从 h5 读出来，
  做一次"每行 log 后减行均值取绝对值"，再写回一个 fold h5。
- 它排在 base 后面，且是 24 次整面板批量作业，不是 1139 万个单元里的任何一步。
  **单股单日口径下，_fold 的贡献是 0 毫秒。**

26.6 毫秒/因子 这个数的分母是 110 个 Rust 因子：
000001@20250303 实测整单元计算 2674ms ÷ 110 = 24.3ms/因子；全市场 20 只抽样均值 1327ms ÷ 110 = 12.1ms/因子。
里面没有 _fold 的位置（真要把 _fold 摊进去，每个单元还要多出 24×26.6=638ms，跟实测总时长对不上）。

hm31 是 4.7ms/因子，但它每个单元出 215 个值，折成"每单元"是 1.01 秒，hm32 是 2.08 秒。
按因子比和按单元比不是一回事。

## 二、_fold 那一段到底多贵（实测）

拿 hm31 的真实 base 面板做（`factor_base/hm31_base/asl_ratio_avg_depth_allday_unfold.h5`，
2472 个交易日 × 5792 只 = 1432 万格，float64）：

| 阶段 | 实测 |
|---|---|
| 读整块面板（h5 → DataFrame） | 71.6 s |
| 算 fold（log、截面均值、取绝对值） | 501.2 s |
| 写回 fold h5 | 244.9 s |
| 合计 | 约 13.6 分钟 / 因子 |

24 个因子按这个速率约 5.4 小时（其中读+写约 2.1 小时）。
**这一段是单进程串行跑的，不吃并行数**（fold 补算在 base 之后一次性做完），
所以不管是 200 还是别的并行，这一段都是这个时间。
顺带验证：按这套代码算出来的值，与库里已经存着的 fold h5 逐格相同（maxdiff = 0.000e+00），
说明复刻的定义是对的。

## 三、那 501 秒不是算法复杂度，是 numpy 的内存行为

同一段代码、同一尺寸（约 1400 万格）在几种条件下的实测：

| 数据 | 计算耗时 |
|---|---|
| numpy，float64，稠密（合成） | 70.7 s |
| numpy，float64，一半是 NaN（合成） | 10.1 s |
| numpy，float32（合成） | 0.48 s |
| **Rust，float64（同一算法，单线程）** | **0.267 s** |
| Rust，float32 | 0.193 s |

同一块数据跑 1/100 尺寸时，float64 只要 0.0055 秒，按比例外推是 1.4 秒，
说明慢不是逐格成本，是整块数组（114MB × 约 5 个临时数组）在这台机器上的分配/带宽悬崖。
生产代码里两条通道正好一条 float32 一条 float64：
框架自带的 fold 通道用 `frame.to_numpy(dtype=np.float32)`（factor_production.py:158），
hm32 自己补算的那条用 `np.float64`（hm32.py:252）。

## 四、搬进 Rust 的代价与收益

**能不能**：能。这个算法就是逐行扫描——每行的 log 值求均值、再减掉取绝对值，
跟股票顺序、跟跨行关系都无关，天然适合单遍 Rust。

**要改多少**：

1. Rust 新增一个函数，输入一块面板、输出 fold 面板（约 60 行），可与现有
   `read_factor` / `save_factor` 一起挂在 `rust_pyfunc` 上。
2. 改三个调用点：`python/rust_pyfunc/factor_production.py:157-180`（框架自带通道）、
   `reports/okay_database/submit/hm32.py:241`（hm32/hm31 的补算）、hm31 那份同款补算。

**收益**：

| | 现在 | 改后 |
|---|---|---|
| 单因子计算 | 501 s（真实面板实测）/ 70.7 s（合成） | 0.27 s |
| 单因子读 + 写 | 316 s | 316 s（不变，是数据盘速度） |
| 24 个因子合计 | 约 5.4 h | 约 2.1 h |

测速条件：单进程、不开并行。fold 补算串行，跟并行数无关。

再把"整面板重读"去掉（框架通道本来就是在写 base 的同一次循环里顺手算 fold，
hm32 这条是自己另起一次），能再省 24 × 71.6s ≈ 29 分钟。

**对 26.6 毫秒/因子 的影响：0。** 那个数字量的是每个计算单元里的 110 个 Rust 因子，
_fold 不在这条路上，搬到哪儿都不会让它变快哪怕 0.1 毫秒。

## 五、hm32 "每因子 26.6ms vs hm31 4.7ms" 的真实原因（复述已提交的测量）

每个时段建一张 n×n float64 矩阵（全天 4828² = 186MB，一个单元建 10 张）再做 5~7 次稠密矩阵乘向量，
占单元计算时间的 99.9%（建矩阵 916~1640ms、乘向量 864~1130ms、读数据 4~21ms）。
改成不建矩阵的 O(n log n) 写法后，计算从 1327ms 降到 16.9ms（全市场 20 只抽样均值，78 倍），
全系列 base（11,399,112 个单元、200 并行，标准值）从 33 小时降到约 0.5 ~ 1.2 小时。
详见 `perf_sandbox/hm32_slow_rootcause.md`。
