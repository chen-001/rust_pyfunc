# hm32 为什么慢：实测定位（不改正式库）

## 一、怎么测的

- 代码：`perf_sandbox/hm32_bench/main.rs`，逐行复刻 `src/okay_database/hm032.rs` 的全部算法，
  加了分段计时，另外写了一个"不建矩阵"的对照实现。
- 样本：20250303 全市场 7240 个文件的等距抽样 20 只（每只跑 2 遍取快的一次），
  原始输出在 `perf_sandbox/hm32_bench/strat_raw.txt`。
- 对照真值：先用 `rp.okay_compute_stock('hm032', code, date)` 在 4 组（日期，股票）上
  拿到 110 个值，和本 bench 算的逐值比对（见下文精度一节）。

## 二、单个"某天某只股票"的耗时构成

000001 @ 20250303（全天有效快照 4828 行）：

| 阶段 | 耗时 | 占比 |
|---|---|---|
| 读 CSV + 解析成 f64 | 3.8 ~ 21 ms | <1% |
| 三列变换（volume.diff 取 log 等） | 0.2 ms | <0.1% |
| 四列标准化 | 0.3 ms | <0.1% |
| 建矩阵：5 个时段各 2 张 n×n 的 f64 | 916 ~ 1640 ms | ~60% |
| 幂迭代里的矩阵乘向量（实际迭代 5~7 次） | 864 ~ 1130 ms | ~40% |

结论：时间全在 n² 上，读取和循环结构都不是瓶颈，内存分配也不是
（`vec![0.0; n*n]` 那一步实测 0.1~0.2 ms，真正贵的是往里写 n² 个元素）。

全天那一张矩阵是 4828×4828×8B = 186 MB，每次 `haha` 要建两张、全天要建 10 张。

## 三、全市场 20 只抽样的均值

| | 均值 | 中位数 |
|---|---|---|
| 现在（建矩阵） | 1327 ms | 1416 ms |
| 改法（不建矩阵） | 16.9 ms | 17.1 ms |
| 倍数 | **78 倍** | 82 倍 |

单只的倍数在 58~147 之间（越是大盘股倍数越高）。

## 四、24 个 _fold 因子不是原因

1. `src/okay_database/hm032.rs` 只产出 110 个 unfold 值，_fold 在 Rust 里根本不算。
2. 24 个 _fold 由 `reports/okay_database/submit/hm32.py:241` 的 `_write_fold_factors`
   在 **base 写完以后**用 Python 补算，一次截面运算，24 个因子合计读写的量约 2.6 GB，量级是分钟。
3. hm31 的 4 个 _fold 走的是同一条路（`hm031.rs:28-44` 有说明）。
4. 它排在 base 后面，不可能造成"跑了 27 小时一份因子数据都没写出来"。

hm32 比 hm31 慢 7.2 倍，差在这一段：hm32 每个时段要建 n×n 密矩阵再做稠密矩阵乘向量（n²），
hm31 是逐笔建价格树（n log n 量级），数据源也不同（盘口快照 3 秒一笔 vs 逐笔成交）。

## 五、改法

M 的每个元素是 |z_i − z_j| 的形式（下三角取 volume 的差值、严格上三角取 price 的差值），
根本不需要把 n² 个元素写出来。一次 M·x 可以这样做：

1. 把这列数值排序，记下每个元素的秩；
2. 按行号顺序把元素一个个插进两棵树状数组（一棵存 x 的和，一棵存 值×x 的和）；
3. 查一次前缀和就能得到 |q − v_j| 的加权和。

代价从 n² 降到 n log n，全天那一档从 23,000,000 次乘法降到约 60,000 次。
代价是每个时段多两次排序（n log n），相对收益可以忽略。

## 六、效果与精度

**效果**

| 口径（并行数写在括号里） | 现在 | 改后 |
|---|---|---|
| 计算段，20 只抽样均值（单进程不开并行） | 1327 ms | 16.9 ms（78 倍） |
| 计算段，000001@20250303 单只（单进程不开并行） | 2352.7 ms | 38.8 ms（61 倍） |
| 计算段，000001@20220819 单只（单进程不开并行） | 1638.6 ms | 33.0 ms（50 倍） |
| 全系列 base（11,399,112 个单元，200 并行） | 33 小时 | 约 0.5 ~ 1.2 小时（折算，非实跑） |

单只的倍数在 58 ~ 147 之间，越是大盘股越高。读数据那一步（4 ~ 35 ms）不变，
所以「含读数据的整单元」倍数会略低于上表的计算段倍数。

全系列那行是折算，不是新跑一遍：33 小时里 99.6% 是计算段（000001 实测拆解，计算 2674ms、读取+变换+标准化 20ms 上下），
计算段缩到 1/78，剩下那 0.4% 不动，得到 33 × (0.996/78 + 0.004) ≈ 0.55 小时；
把没量到的每单元写盘开销算 2% 的话，上限约 1.2 小时。

**精度**

- 与旧实现逐值比对，110 个值里最大绝对差 4.5e-12（值域到 5500，相对 8e-16）。
- 与库里 `okay_compute_stock` 的真实输出比对 4 组（20250303:000001、20250304:600519、
  20180601:000002、20231020:300750）：本 bench 的旧算法版和新算法版**与库的差异完全相同**
  （1.3e-4~2.2e-4），也就是差异全部来自库里把结果存成 f32 这一步，新算法本身没有引入任何可见偏差。
- 2.2%（157/7240）的股票-日输入里有非有限值（某时段标准差为 0 等），
  那一小部分保留原来的稠密路径兜底，行为逐位不变；全系列代价约 0.45 小时。

## 八、并行数

本文所有数字都在这两个并行条件下取得，不留隐含假设：

- 单股单日、单因子：**单进程、不开并行**（用户的验收标准，20220819 那档也是这个条件）。
- 全系列折算：**200 并行**，即 cross-section-pipeline / rust-pipeline-level2 的标准值。

提速全部来自算法（不建矩阵），不依赖加并行。加并行不是本次优化的一部分，以后也不作为提速手段。
