## 三、瓶颈：两个组内平方循环，占 89%

| 循环 | 距离元素总数 | 耗时 | 每元素 |
|---|---|---|---|
| ultra_sorted 主循环 | 479,220,872 | 7,575.0 ms | **15.8 ns** |
| price_stats_v3 主循环 | 1,240,600,102 | 18,143.3 ms | **14.6 ns** |
| 合计 | **1,719,820,974** | **25,718.3 ms** | 15.0 ns |

**这两个循环占总耗时的 89.3%（25,718.3 / 28,809.6 ms）。**

## 四、是复杂度，不是循环写法，也不是内存分配

判定依据是"两组对照"，两边处理的是同一种数据（组内每条记录 × 全部同组目标记录）：

| | ultra_sorted 主循环 | price_stats_v3 主循环 |
|---|---|---|
| 距离元素总数 | 479,220,872 | 1,240,600,102 |
| 每元素耗时 | 15.8 ns | 14.6 ns |
| 记录数 | 102,387 | 255,996 |
| 平均目标集大小 | 4,680 | 4,846 |
| **Vec 申请次数** | **307,161**（每条记录 2 个 + all_prices） | **426**（每组复用 1 个 buffer） |
| sort / select 次数 | 204,774 | 512,844 |

- **内存分配不是瓶颈**：分配次数相差 721 倍（307,161 对 426），每元素耗时只差 8%（15.8 对 14.6 ns）。
  如果分配是主导项，复用 buffer 的那一边应该快得多，实测没有。
- **循环写法（每条记录克隆一次目标下标、push 一次距离数组）也不是主导项**：
  按元素算，两种写法的成本几乎一样。
- **是元素总数**：17.2 亿个 (时间距离, 价格) 二元组。
  元素数正比于「组内记录数的平方」——组内记录数 m 的组贡献 m² 个元素，
  平均每组 4,680 ~ 4,846 个元素，就是 m² 的量级。
  17.2 亿 × 15.0 ns = 25.8 s，与实测 25.7 s 吻合。

## 五、其余阶段合计只有 3.09 s（10.7%）

读 CSV + 解析 41.2 ms（24.4 MB → 592 MB/s）、变换与分时段 9.6 ms、
建订单表与分组 29.9 ms、dropna 与拆两侧 153.4 ms、回填 n×27 38.4 ms、
features_f64 1,164.0 ms、16 个 extend 块 1,646.2 ms。
**I/O 完全不是问题。**

## 六、方法（可复现）

- 目录 `perf_sandbox/hm076_bench/`，crate `hm076_bench`（ndarray 0.15 + rayon 1.8，cargo --release --offline）。
- 三个模块用 `#[path]` 指向正式库源码的副本：`data_paths.rs`（原样）、`features_f64.rs`
  （只砍掉末尾的 pyo3 验证包装，计算部分原样）、`hm076.rs`（原样 + 插桩）。
  `lyapunov` 走 panic 桩——hm076 传的是 `with_lyapunov_exponent=false`，实跑未触发，
  且 77 个值全等可以反证没走那条路。
- 正式库文件一个字没改，没有跑 `./alter.sh`，没有碰 PID 2338178。
- 原始输出：`bench_final.txt`（计时+取值）、`ref_out.txt`（库取值）、`compare.py`（比对）。
- 三次读数 29,390 / 29,305 / 28,810 ms，本报告用最快那次。
