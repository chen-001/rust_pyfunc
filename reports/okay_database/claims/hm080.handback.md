═══ 二、两个卡点（我实测到的数字）═══
拿 20250303 000001（56193 行 → combined 56042×64）跑：
  old.get_features_factors(...) vs rp.verify_get_features_factors_rust_f64_ex(...)
  长度 3754 / 名字完全相同；分块看：
    stats 块 1152 个：最大相对误差 2.8e-12，全过 ✓
    corr  块 2346 个：320 个超 1e-4，最大相对误差 1.99 ✗

  (1) corr 块：旧代码的 append_for_corr 是**错位对齐**的
      combined 的 index 是 0..56041，而 append 是 td.tail(56042)，index 是 151..56192。
      pd.concat([df, append], axis=1) 按 index 做 outer join ⇒ 结果 56193 行，
      只有 index 相同的位置上两边才有值，于是「combined 列 × append 列」的相关系数
      实际只用 151..56041 这一段。库里 f64 通路拿到的是两个对齐好的矩阵，算出来的是
      正常的成对相关系数，所以整块对不上（不是精度问题，是数据对齐问题）。
      复现办法：给 full_ex 传 pad 到 56193 行的两份矩阵——
        data_padded[i]   = combined[i]   (i<56042)，其余全 NaN
        append_padded[i] = td 第 i 行     (151<=i<=56192)，其余全 NaN
      成对丢 NaN 之后正好等价于那次 outer join；stats 块是按列统计，末尾补全 NaN 行不影响
      （autocorr/trend 的有效点集合不变）；但**必须确认 full_ex 允许 data 与 append 行数
      相同且 data 里出现整行全 NaN**。要动 features_f64 的话记得 hm090 一起重验。
  (2) extras 块：lz_complexity / entropy_1d / max_range_product 在含 NaN 的列上不一致
      （Rust 先滤 NaN、老库把 NaN 也算一个 bin），REMAINING.txt 里已经记过这个公共缺口，
      要求让 f64 通路向老库对齐并**把 hm090 一起重验**。hm080 的 names_save 里有
      entropy_1d / max_range_product / lz_complexity 的名字，绕不过去。
